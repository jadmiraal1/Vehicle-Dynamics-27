# Contributing

`targets/run_*.m` turn the models into numbers other subteams design against,
so **a wrong number here becomes a part someone machines.** When you are not
sure about a result, say so in the code and in the printed assumptions rather than
quoting a confident figure.

Read `README.md` first, then `docs/STATUS.md` for what each model can and
cannot do.

## Before you push

```matlab
vd_setup
vd_selftest      % relationships: is the physics still wired up correctly?
vd_golden        % values: did any number this repo produces change?
```
```bash
python3 tests/ci_checks.py      % has anything drifted out of sync?
```

CI runs all three on every push and pull request.

**When `vd_golden` reports drift, that is not automatically a bug.** It lists
which values moved and by how much. Read the list. If every line is a change
you intended, run `vd_golden('bless')` and commit the updated
`tests/refs/golden_<CAR>.tsv` **in the same commit as the code**. If any line
surprises you, stop and find out why before blessing.

## Workflow

- One change per branch; open a pull request and wait for CI to pass.
- Keep a physics change and a refactor in separate commits, so a moved number
  can be traced to its cause.
- Explain in the pull request why any golden value moved.
- Line endings are LF for all source and text files (`.gitattributes`); do not
  override this locally.

## Where numbers live - one home each

| kind of number | its one home |
|---|---|
| measured or decided about *this car* | `cars/config_<CAR>.m` |
| fitted from tire data | `tire/`, written to `tire_coeffs_<CAR>.mat` |
| set by the competition rules | `util/fsae_rules.m` |
| unit conversions | `util/vd_const.m` (hot loops read the cached `p.N_PER_LBF`) |
| pure arithmetic on inputs | `util/vd_derive.m` |
| one operating point | `models/` |
| over a lap | `lapsim/` |
| a study result (target) | `targets/run_*.m` |

- **Change a car property in `cars/config_<CAR>.m`**, never in
  `vehicle_params.m` (which holds only universal constants, model switches and
  the defaults). For a one-off "what if", edit nothing:
  `out = run_lap_targets(vd_set(vehicle_params(), 'm_car', 240))`.
- **Never hand-edit** `tire_coeffs_<CAR>.mat` or `tests/refs/*.tsv`. Both are
  generated; regenerate them.
- **Do not re-implement what exists.** One function each for: 75 m acceleration
  (`lapsim/accel_time.m`), braking limit (`models/ax_limit.m`), normal loads and
  resistances (`models/road_loads.m`), camber factors (`models/tire_camber.m`),
  one tire (`models/tire_forces.m`), scoring (`util/fsae_points.m`). If you are
  about to copy a formula, extract it into a function instead.

## Things that will bite you

- **`p` holds plain values only** - numbers, text, logicals and structs of
  those. Never an object, a `containers.Map` or a handle. MATLAB copies structs
  on assignment, which is what lets `vd_set` return a modified car without
  touching the original; a handle would leak changes between cars in a sweep.
- **`mu_of_load` is a hot path** (~10^5 calls per g-g-V surface). Keep its
  argument checks cheap; put slow, helpful checks behind the failure branch.
- **Units change at the boundaries.** SI everywhere except the tire interface,
  which is lbf and degrees (the TTC rig is imperial). Accelerations are in g at
  function interfaces and m/s^2 inside solvers: `load_transfer(p, ay, ax)` takes
  g. Imperial names carry a suffix (`_lbf`, `_deg`); no suffix means SI.
- **Camber sign:** `gamma > 0` means the tire leans so camber thrust *adds* to
  the cornering force - the loaded outside wheel, which is *negative* camber in
  the SAE chassis convention. See `models/tire_camber.m`.
- **Setting a field directly bypasses the derived values.** `q = p; q.m_car = 240`
  leaves `m`, `k_rot`, `Izz` and the axle loads describing the old car. Use
  `vd_set`. (The studies set a few fields directly on purpose: inputs nothing
  is derived from, such as `LLTD` or `ClA`, and `P_max` as an endurance power cap.)

## The tire artifact and what CI cannot see

`tire_coeffs_<CAR>.mat` is generated by `build_tire_coeffs` from `TTC_Data/`
and stamped with a hash of its inputs; `vd_selftest` refuses a stale one.

`TTC_Data/` is licensed to registered teams and must **never** be committed or
shared outside the team. CI therefore has no tire data:

- CI cannot rebuild the artifact or check its hash. It tests everything
  downstream of the committed artifact.
- **After editing anything in `tire/`, rebuild and run `vd_selftest` on a
  machine that has the data, before pushing.** `tests/ci_staleness.py` only
  checks the bookkeeping: if a hashed source changed, the artifact must change
  in the same pull request.
- The fit needs the **Optimization Toolbox**. `build_tire_coeffs` refuses to run
  without it, because the `fminsearch` fallback gives a different tire.

## Adding a target

CI enforces all four:

1. `targets/run_<thing>_targets.m`, taking `p` and returning a struct.
2. It prints an **"Assumes:"** line that states what its numbers rest on (see
   Printed output below).
3. It is listed in the script table in `README.md`.
4. It is in `TARGETS` in `tests/vd_golden.m`.

Wrap plotting in `if vd_plots()` so the tests run without drawing.

## Code style

- MATLAB R2019b or newer. One function per file, named after the file.
- Each file starts with a help block: what it computes, how to call it,
  inputs and outputs with units, and the assumptions it makes.
- Comments explain *why* and give the physics a newcomer needs, not a history
  of the code (that belongs in commit messages).
- Long, descriptive names over clever abstractions. Units in names or comments.
- Mark provisional inputs `PROVISIONAL`, decisions `CHOICE`, unchecked carry-over
  `[verify]`. Say in the printed Assumes line when a model cannot see something.

## Printed output

What a script prints is read by people who did not write it.

- Start with one title line: what the study is, the car, the key inputs.
- One result per line with `vd_row(label, value, note, status)`: a plain-words
  label, the value with its unit, optional context ("now 0.279 m"), and a
  verdict in capitals where there is a requirement (`OK`, `TOO HIGH`, `FAILS`).
- End with an `Assumes:` line (CI checks for it).
- No internal shorthand: no tracker item numbers or codes (CI checks), no
  variable names in place of words, no instructions aimed at one subteam.
- Warnings from functions that run thousands of times per study go through
  `vd_warn`, which prints each one once per run; start every `run_*` script
  with `vd_warn('reset')`.
